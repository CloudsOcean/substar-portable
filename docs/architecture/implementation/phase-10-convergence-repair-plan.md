# Substar 综合收敛修复与验收计划

> 状态：v2 破坏性切换已实施；正在执行最终发布门禁
> 编制日期：2026-08-30  
> 适用代码库：`C:\temp\Substar\substar-portable-repo`  
> 测试素材：`C:\temp\R01_No Music_Map_Animation.mp4`、`C:\temp\参考文稿.docx`

## 1. 文档目的

本计划用于一次性收敛 Substar 当前暴露出的系统性问题，包括：

- 施工图、运行实现和发布产物不一致；
- 开发目录与便携版生产仓库长期分叉；
- 切分、校准、翻译分别维护模型配置、任务状态和进度；
- 多层重试形成事实上的多次修复；
- 局部失败时成果丢失、任务卡卡死或缺少可编辑目标行；
- 项目目录混合创建任务、耐久数据、活动状态、审计和缓存；
- 巨型文件职责失控，但又不能为了文件尺寸盲目重写；
- 测试和发布门禁无法充分证明真实便携版能够完成完整流程。

本计划是后续实施和验收基线。现有 `docs/architecture/target/` 仍描述此前冻结的目标架构；在本计划完成并验收前，不得把本计划中的目标状态标记为“已经实现”。

## 3. 冻结的产品不变量

### 3.1 用户术语

- UI、日志、设置和用户文档统一使用“修复”。
- 新任务契约使用 `repair`。
- v2 不读取旧项目中的 `fallback`、`repairing`；旧数据原地保留但不进入项目发现。

### 3.2 一项任务只进入一次修复阶段

正式生命周期：

```text
主处理全部单元
→ 收集失败单元
→ 最多进入一次修复阶段
→ 仍未解决的单元转人工处理
```

必须持久化：

```text
task.repair_phase_entered: boolean
unit.primary_request_count: integer
unit.repair_attempted: boolean
unit.repair_request_count: integer
unit.transport_attempt_count: integer
```

规则：

- 进入修复前先提交 `repair_phase_entered=true`；
- 发起单元修复前先提交 `repair_attempted=true`；
- 后端重启、恢复、重复回调和页面刷新不得重新授予资格；
- 每个失败单元 `repair_request_count <= 1`；
- 禁止修复再次调用修复；
- 删除次数型 `segmentation_repair_attempts`、`translation_repair_attempts` 的产品语义；
- 次数型旧配置不迁移、不读取；v2 只有任务级布尔修复资格。

### 3.3 传输重试不等于内容修复

- 每个语义请求只有一次主调用；
- 每个失败单元最多一次内容修复调用；
- 每个语义调用最多两次传输重试；
- 传输重试必须复用请求幂等键；
- 鉴权、配置和能力错误不重试、不修复；
- 输出截断不循环扩大预算，直接进入唯一一次修复；
- 禁止业务层、Stage 编排器和 Provider 适配器分别套重试循环；
- 审计必须能够证明实际模型调用次数。

### 3.4 局部失败不能阻断交付

- 切分：保留成功切点；失败区间按原始时间和原文字生成问题 Cue；
- 校准：保留成功校准；失败块继续使用原字幕；
- 翻译：保留成功译文；每个失败源 Cue 都生成可编辑空目标槽位；
- 不得用源文冒充译文；
- 修复只能处理未解决单元，不得重新覆盖成功单元；
- 局部失败终态为 `succeeded_with_issues`；
- 只有无法生成基础可编辑文档时才使用 `failed`。

翻译未解决槽位至少包含：

```json
{
  "target_text": "",
  "translation_status": "manual_required",
  "issue_code": "translation_unresolved",
  "editable": true
}
```

人工补填必须支持保存、撤销、重做、导出、重新导入、刷新和后端重启。

### 3.5 AI 审阅已经外置

- 不进入内部 Task Runtime；
- 不占项目 AI 锁；
- 新项目不写 `stage_review_*`；
- 新工程导出不携带内部 `review/`；
- v2 项目不写入或读取内部审阅字段；旧项目整体不进入 v2。

## 4. 目标运行架构

### 4.1 唯一 ModelGateway

切分、修复、校准、翻译和 Qwen AI 智能填写只能通过统一模型入口调用文本模型。

冻结的 `StageRequest` 至少包含：

```text
provider
model
credential_reference
thinking_mode
reasoning_effort
output_limit
timeout
task_id
unit_id
idempotency_key
```

ModelGateway 统一负责：

- Provider 能力映射；
- API Key 引用解析与注入；
- GLM 无非思考模式时在任务创建前映射为 thinking-low；
- 普通正文、`reasoning_content`、流式和非流式响应解包；
- 合法空响应与真正空输出的统一判断；
- 错误分类；
- 唯一传输重试实现；
- 脱敏请求审计；
- 调用次数和耗时统计。

连接测试与正式 Stage 必须复用同一个能力映射和响应解包器。

### 4.2 统一 Task Runtime

正式长任务：

- 字幕创建；
- AI 校准；
- 字幕翻译。

统一状态：

```text
queued
running
cancelling
succeeded
succeeded_with_issues
failed
cancelled
interrupted
```

统一任务快照：

```text
task_id
project_id
kind
state
phase
units
overall_progress
message
error
needs_attention
started_at
updated_at
owner_pid
heartbeat_at
```

活动任务、进度、锁和心跳只归 Task Runtime；项目目录不再保存第二份活动状态。

### 4.3 统一任务租约

使用上下文管理器管理项目 AI 独占权：

```text
with editor_ai_task_lease(project_id, task_id):
    run_task()
```

要求：

- 初始化失败、线程异常、取消和写盘错误都在 `finally` 收口；
- 锁记录 PID、心跳和更新时间；
- 后端重启能够判断孤儿锁；
- 详细任务终态和成果先写入，最后释放锁；
- 同一项目校准和翻译互斥，但不同项目遵守 Worker 并发配置。

### 4.4 错误分类

统一错误码：

- `auth_terminal`；
- `configuration_terminal`；
- `capability_terminal`；
- `transport_retryable`；
- `rate_limit_retryable`；
- `output_truncated`；
- `contract_invalid`；
- `cancelled`。

只有 `contract_invalid` 和允许修复的 `output_truncated` 进入一次修复。密钥错误和模型能力错误不得让修复阶段“修配置”。

## 5. 三类任务生命周期

### 5.1 字幕创建

```text
排队
→ 媒体准备
→ ASR
→ 程序切块
→ AI 切分 0/n
→ 修复 0/m（仅在 m > 0 时进入）
→ 生成可编辑文档
→ 原子发布项目
→ 交付
```

ASR 和程序切块不重写内部算法，只接入统一任务进度与终态。

### 5.2 AI 校准

```text
排队
→ 准备输入
→ 主处理 0/n
→ 修复 0/m
→ 校验结果
→ 写入项目新修订
→ 写入运行审计
→ 交付
```

### 5.3 字幕翻译

```text
排队
→ 准备逐行单元或意义组
→ 主处理 0/n
→ 修复 0/m
→ 校验映射
→ 生成目标槽位
→ 写入项目新修订
→ 写入运行审计
→ 交付
```

## 6. 统一任务卡片

### 6.1 出现条件

| 页面 | 任务 | 出现条件 |
|---|---|---|
| 切分页 | 字幕创建 | 创建请求被后端接受 |
| 切分页 | AI 校准 | 任意项目存在活动校准任务 |
| 切分页 | 字幕翻译 | 任意项目存在活动翻译任务 |
| 编辑页 | AI 校准 | 当前项目存在活动任务或需要处理的终态 |
| 编辑页 | 字幕翻译 | 当前项目存在活动任务或需要处理的终态 |
| 编辑页 | 简繁转换、参考文稿 | 用户启动短操作 |

切分页不再按 `project_id` 把创建、校准和翻译合成一张会改变身份的卡片。允许按项目视觉分组，但每项任务有独立 `task_id` 和独立卡片。

### 6.2 一个组件，两种密度

统一 `TaskProgressCard`：

- 切分页使用完整布局，显示项目名、任务类型、阶段、计数、错误复制和操作；
- 编辑页使用紧凑布局，省略重复项目名；
- 两种布局共享状态颜色、阶段、计数、百分比、错误和终态规则；
- 两页读取同一个任务快照，不重新推导进度。

短操作使用 `OperationCard`：

- 只显示处理中、完成、失败；
- 不伪造 `0/n`；
- 不进入切分页全局队列；
- 不进入修复阶段。

### 6.3 进度规则

| 任务 | 阶段范围 |
|---|---|
| 字幕创建 | 准备 0–5、ASR 5–45、程序切块 45–50、AI 切分 50–80、修复 80–90、交付 90–100 |
| 校准/翻译 | 准备 0–5、主处理 5–75、修复 75–90、校验与交付 90–100 |

- 已知数量时显示 `完成数/总数`；
- Provider 不提供 ASR 细进度时显示动态条、真实阶段和等待时间，不伪装成 0%；
- `m=0` 时修复标记为已跳过；
- 进度只能单调增加；
- 所有成果、审计和状态持久化成功后才能到 100%；
- `succeeded_with_issues` 保持黄色并提供“打开问题字幕”；
- 干净成功重新打开项目时不重复弹旧卡片。

## 7. 翻译模式产品化

编辑器 AI 翻译菜单增加任务级选择：

### 7.1 逐行翻译

- 一个源 Cue 对应一个目标 Cue；
- 模型可读取前后文，但禁止改变 Cue 拓扑；
- 输出按 `cue_id` 验证无重复、无遗漏；
- 缺失单元进入唯一一次修复；
- 仍缺失则生成可编辑空目标行。

### 7.2 多对多翻译

- 保留现有意义组映射；
- 允许多个源 Cue 对应多个目标行；
- 有效意义组立即保留；
- 只修复缺失或非法意义组；
- 未解决源 Cue 分别生成可编辑空目标行。

### 7.3 模式规则

- 默认保持多对多翻译；
- 模式在任务创建时冻结；
- 模式缺失是无效 v2 任务输入，不从旧项目推断；
- 任务审计、运行报告和导出说明记录模式；
- 两种模式共享凭据、思考、错误、修复和部分交付规则。

## 8. 项目数据结构 v2

### 8.1 创建任务与正式项目分离

```text
data/.substar-workbench/task-runtime/<task_id>/
data/projects-v2/<project_id>/
```

- 上传和处理中只创建 job；
- 基础可编辑文档验证成功后由 Finalizer 原子发布为 project；
- 失败 job 可重试或清理，不进入最近项目；
- 发布失败不得留下半个正式项目。

### 8.2 正式项目结构

```text
projects-v2/<project_id>/
├── project/
│   ├── manifest.json
│   └── project.sqlite3
├── input.<ext>
├── reference.<ext (optional)>
├── recognition_evidence.json
├── task_info.json
├── project_creation.json
└── run-specific durable audits
```

### 8.3 根级资产清单

`project/manifest.json` 与根级任务信息共同记录：

- 项目格式版本、数据库格式版本、项目 ID、文档 ID；
- 原媒体与可选参考稿的规范相对路径；
- SQLite 路径和当前修订 ID；
- 听写证据路径、格式和 SHA-256；
- 可选参考稿路径和 SHA-256；
- 创建配置摘要；
- Prompt 快照哈希；
- 创建时间、更新时间和冻结任务配置。

打开项目只按清单验证，不扫描目录猜测资产。

### 8.4 媒体重新关联

- 缺少原媒体时进入明确的“需要重新关联媒体”状态；
- 播放缓存不能冒充源媒体；
- 用户选择新文件后校验类型、大小、时长和可用哈希；
- 重新关联写入新清单修订并保留审计。

### 8.5 缓存治理

- 播放代理按源媒体 SHA-256 寻址；
- 播放代理、波形和中间 WAV 位于全局 `.cache/`；
- 设置总容量上限和 LRU 淘汰；
- 设置页显示缓存占用并提供清理；
- 清理只删除可重建数据；
- 清理测试必须证明不会删除媒体、SQLite、参考稿和听写证据。

### 8.6 可安全精简项

- 新修订停止写未被读取的 `inverse_patch_blob`；
- v2 数据库不读取旧 schema；旧数据库只在磁盘原位保留；
- 重复 Prompt 目录合并为一份内容寻址快照；
- `translation/latest.json` 不复制 SQLite 中的完整译文；
- 校准 latest 与 audit 收敛到对应 run；
- `translation_report.json` 归入对应 run；
- 创建配置删除失效 relay profile、整份 Provider 展示目录、动态 URL、重复文件列表、外置审阅设置和重复长度限制。

### 8.7 不得删除的数据

- 原媒体；
- 原始词级听写证据；
- 项目 SQLite 正向修订历史；
- 已成功的部分切分、校准和翻译；
- 失败单元的可编辑目标槽位；
- 每次 AI 运行的最小请求、冻结模型配置、结果和错误审计；
- 唯一失败证据。

运行审计可以保留最近 N 次，但不得删除仍是唯一失败证据的 run。

### 8.8 三种导出

- v2 字幕工程：当前修订、媒体、参考稿和必要证据；只允许导入 v2 工程；
- 完整备份：全部 SQLite 修订历史和运行审计；
- 字幕导出：SRT、TXT 等交付文件。

三种导出必须在 UI、文件结构和验收中明确区分。

## 9. 源码与施工图收敛

### 9.1 唯一生产源码

- 以便携版仓库的已验证生产提交为合并基线；
- 逐项审查旧开发目录中的未合并修改，禁止整文件覆盖；
- 将确认有效的修改合入生产仓库；
- 将生产提交收敛到 `main`；
- 后续 tag 只能从 `main` 创建；
- 发布分支只用于短期稳定，不作为永久真相源；
- 旧开发目录转为归档或明确标记为非生产。

### 9.2 按业务边界拆分巨型文件

`http_api.py` 目标边界：

- media routes；
- document command routes；
- tutorial routes；
- exchange routes；
- calibration routes；
- translation routes。

`editor.js` 目标边界：

- 时间轴与播放；
- Cue 编辑与版本；
- TaskProgressCard；
- 校准；
- 翻译；
- 教程；
- 导入导出。

要求：

- HTTP 层只负责请求解析、权限/修订校验和响应；
- AI 算法和业务编排进入 application service；
- 不为了行数机械拆分；
- 不引入微服务、消息队列或新数据库；
- 从实验脚本中抽出仍被生产代码调用的物化逻辑。

### 9.3 施工图语义门禁

现有 system map 检查主要验证模块、符号和生产者/消费者关系。新增语义测试：

- 所有单元 `repair_request_count <= 1`；
- 所有终态任务不存在活动 AI 锁；
- 所有模型请求都有 provider、model 和 credential reference；
- 项目资产只能由 `project.json` 定位；
- Task Runtime 是活动状态唯一来源；
- tag version 等于 manifest 和界面版本；
- 真实视频 E2E 不是 `not_run`。

## 10. 破坏性切换策略

- 新项目只写 `data/projects-v2` 与 v2 契约；
- v2 不扫描、读取、导入、迁移或规范化旧项目；
- 旧 `data/projects` 原地保留，但不出现在最近项目、编辑器列表或直接 URL 中；
- 旧 Runtime、状态文件、凭据别名、修复次数和审阅字段不授予任何 v2 行为；
- 不存在隐式迁移、惰性迁移、兼容默认值或旧字段转换；
- 需要历史内容时由用户在旧版本中导出普通媒体/字幕，再作为全新 v2 项目创建；
- Git 历史是旧实现唯一代码归档，发布包不携带 importable legacy 模块。

## 11. 自动化测试

### 11.1 模型和凭据

- GLM 不支持非思考时冻结为 thinking-low；
- DeepSeek/GLM 切换后所有 Stage 使用正确模型和密钥引用；
- Qwen AI 智能填写遵守相同能力规则；
- Qwen Prompt、临时热词和语言 hint 实际进入听写请求；
- `content`、`reasoning_content`、合法空响应处理一致；
- 日志和运行审计不泄露 API Key。

### 11.2 修复和请求预算

- 主处理失败后任务最多进入一次修复阶段；
- 每个失败单元修复请求最多一次；
- 重启和重复回调不重置资格；
- 鉴权、配置和能力错误不进入修复；
- 传输重试不增加语义修复次数；
- 不存在外层、Stage 和 Provider 三重重试；
- 成功单元不会被修复覆盖。

### 11.3 生命周期与任务卡

- 校准和翻译不会停在 0%；
- 切分页与编辑页显示同一个 task ID、计数和终态；
- 页面切换不创建重复任务；
- 修复 `m=0` 时显示已跳过；
- 终态持久化后才释放锁；
- 取消、异常和后端重启后锁正确恢复；
- 干净成功、含问题成功和整体失败的卡片行为正确。

### 11.4 部分成果

以 10 个翻译单元、3 个失败为固定案例：

- 7 个成功译文完全保留；
- 3 个失败 Cue 有空白可编辑目标行；
- 问题导航能定位；
- 人工填写后可保存、撤销、重做和导出；
- 刷新与重启后结果一致；
- 状态为 `succeeded_with_issues`；
- 修复没有重新处理 7 个成功单元。

### 11.5 项目格式与缓存

- 旧项目不可发现、不可打开，直接 URL 返回明确的不支持或 404；
- 原媒体缺失时要求重新关联；
- 清缓存不会删除耐久数据；
- 新项目没有重复 Prompt；
- 新修订不再新增逆向补丁；
- 活动状态只存在 Task Runtime；
- 三种导出内容边界正确。

## 12. 真实素材端到端验收

### 12.1 素材

- 视频：`C:\temp\R01_No Music_Map_Animation.mp4`；
- 参考稿：`C:\temp\参考文稿.docx`；
- 测试复制到隔离数据根目录，不修改原文件；
- 使用便携版内置 FFmpeg 检查视频、时长、编码和音轨；
- 记录视频、参考稿 SHA-256 和参考稿有效段落数。

### 12.2 正常完整流程

1. 在完整网络和 FFmpeg 环境启动便携版后端；
2. 创建 AI 切分＋参考文稿辅助项目；
3. 验证 Qwen Prompt、热词和语言 hint 的脱敏请求审计；
4. 完成 ASR；
5. 完成程序切块；
6. 完成 AI 语义切分；
7. 原子发布可编辑项目；
8. 验证媒体、波形、Cue 和参考文稿标记；
9. 完成 AI 校准；
10. 项目 A 从校准后的同一修订完成逐行翻译；
11. 另建项目 B，仅执行 AI 切分，在编辑器注入参考稿后完成多对多翻译；
12. 检查问题字幕、目标输入框、任务卡和运行审计；
13. 完成人工补填、保存、撤销、重做；
14. 导出并重新导入字幕；
15. 重启后端后重新打开项目；
16. 导出 v2 字幕工程并在全新 v2 数据根目录导入。

### 12.3 确定性故障注入

通过 ModelGateway 测试适配器注入，不直接损坏原素材：

- AI 切分缺少一个块；
- 校准返回一个非法块；
- 逐行翻译遗漏一个 Cue；
- 多对多翻译返回部分非法意义组；
- 输出截断；
- 网络超时；
- 限流；
- 无效密钥；
- 不支持的思考参数；
- 成果写入前进程中断；
- 终态写入后、锁释放前进程中断。

每项验证：

- 是否允许进入修复；
- 修复是否只发生一次；
- 成功成果是否保留；
- 未解决内容是否可编辑；
- 锁和终态是否一致；
- 刷新和重启后是否保持一致。

## 14. 发布硬门禁

以下任一项失败，不得发布：

- Python、前端、契约、旧格式拒绝测试未全绿；
- 真实视频的切分、校准和两种翻译未全部完成；
- 故障注入没有证明修复实际工作；
- 任一单元 `repair_request_count > 1`；
- 终态任务仍持有活动 AI 锁；
- 存在 0% 假运行或两个页面状态不一致；
- 局部翻译失败没有可编辑空目标行；
- 旧项目仍可被 v2 发现/读取，或媒体重新关联、缓存清理失败；
- 真实 E2E 在构建记录中仍为 `not_run`；
- 工作区不干净；
- tag 不来自 main；
- tag、manifest、UI、更新日志和包版本不一致；
- 完整权限环境下 FFmpeg 或网络不可用；
- 发布包没有 SHA-256 和对应源码提交。
